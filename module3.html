Модуль 3

AI-assisted SDLC с coding agents

Цель модуля — научиться работать с coding agent как с управляемым процессом: правила → спецификация → реализация с тестами → проверка → PR. Результат модуля — способ работы, а не код. Поэтому проверяются артефакты: файлы правил, спецификация, история коммитов, журнал docs/notes.md, PR и заметка о решениях.

Как проходить модуль. Сначала курсы теории, затем задания 3.1–3.5. Задание по теме, которую вы уверенно знаете, можно пропустить: итоговое задание покажет, если в ней есть пробел. Модуль засчитан, когда итоговое задание выполнено по всем критериям.
Как проверяется. Все задания, включая итоговое, вы проверяете сами. Порядок: сделали задание → прошли по критериям готовности → только потом открыли пример решения и сравнили. Каждый критерий проверяется командой, через git или по записи в docs/notes.md. Если критерий не выполнен, вернитесь к заданию, а не к решению.
Инструмент и стек: основной инструмент — Claude Code. Copilot и Cursor встречаются в задании 3.1 и в необязательном сравнении. Учебный проект: TypeScript, Node.js 20+, Express, Vitest, ESLint.

Учебный проект

Team Tasks

Небольшой готовый сервис задач команды. Все задания модуля и итоговое задание выполняются в нём, поэтому рабочий проект не нужен. Проект создаётся одним скриптом.

Что заложено в проект

Что Где Для чего
Процент выполненных задач считается неверно src/stats.ts 3.2: тесты с бизнес-смыслом
GET /tasks/recent падает с ошибкой src/storage.ts 3.2: исправление по промпту «ошибка + код + ожидаемое»
Пагинация пропускает первую страницу src/storage.ts 3.4: «сначала тесты»

.env с фейковым секретом корень проекта 3.5: hook, запрещающий чтение
Всего один тест tests/api.test.ts весь модуль
BACKLOG.md с тикетами T-1…T-7 корень проекта задания и итоговое задание
Журнал модуля с разделами по заданиям docs/notes.md промпты, ошибки агента и решения; по нему вы проверяете себя

Задание 3.1

Правила агента: проект и личные

Курсы: Claude Code in Action; GitHub Copilot Capabilities; Cursor Basics 101; AI-Native SDLC; Structured Vibe Coding Время: ~50 мин
Что делаем: настраиваем постоянные правила для агента на двух уровнях. Зачем: без правил агент каждый раз пишет «типовой» код и спрашивает одно и то же. Правила проекта общие для команды и лежат в репозитории, личные — только ваши и в репозиторий не попадают. Агент знает популярный стек (Express, Node) по открытому коду, а всё своё в проекте, как логгер src/log.ts, ему нужно описать.

Условие

  1. До правил. В новой сессии Claude Code попросите добавить логирование в обработчик POST /tasks/:id/done и посмотрите, чем агент логирует. Откатите правку: git restore ..
  2. Создайте CLAUDE.md: стек, команды запуска и проверки, конвенции (логгер src/log.ts, тесты в tests/), запреты (не менять файлы вне задачи, не добавлять зависимости без запроса, не делать push и merge).
  3. Создайте CLAUDE.local.md с личным предпочтением для этого проекта (например, своя команда запуска тестов) и убедитесь, что он не коммитится.
  4. Добавьте личное правило для всех проектов в ~/.claude/CLAUDE.md, например «отвечай кратко, без пересказа сделанного». Это аналог User Rules в Cursor.
  5. Перенесите правила проекта в .github/copilot-instructions.md и .cursor/rules так, как требует каждый инструмент.
  6. После правил. В новой сессии повторите просьбу из шага 1 и сравните результат.
  7. Правила развиваются. До конца модуля, когда агент повторяет одну и ту же ошибку, добавляйте правило в CLAUDE.md отдельным коммитом.

В Copilot и Cursor

Правила проекта.
  • Аналог: в Copilot — .github/copilot-instructions.md, в Cursor — .cursor/rules/*.mdc. Оба читают и AGENTS.md в корне репозитория. Файл попадает в контекст каждого запроса сам, его не нужно прикладывать.
  • С чем путают: общий шаблон промпта, который каждый копирует вручную, — его забывают и меняют под себя. Правила в комментариях исходников агент видит, только когда открыт этот файл. Смена модели не помогает: никакая модель не знает конвенций вашего проекта.
  • Если есть Copilot (необязательно): откройте проект в VS Code и спросите в режиме Ask: «каким логгером пользоваться в этом проекте?» В ответе должен быть src/log.ts, а в списке ссылок под ответом — файл .github/copilot-instructions.md.
  • В журнал: чем файл правил в репозитории лучше общего шаблона промпта.
Личные правила для всех проектов.
  • Аналог: в Cursor — User Rules (Cursor Settings → Rules): хранятся в настройках редактора и действуют в каждом проекте. В Copilot — пользовательские instructions в настройках VS Code.
  • С чем путают: Project Rules (.cursor/rules/*.mdc) лежат в репозитории и действуют на один проект для всей команды. Team Rules задаёт организация централизованно. AGENTS.md тоже лежит в репозитории — это правила проекта, а не личные.
  • В журнал: куда вы положили бы правило «отвечай кратко» в Cursor и почему не в .cursor/rules.

Критерии готовности

  • CLAUDE.md короче 60 строк и содержит 4 раздела: стек, команды, конвенции, запреты.
  • git status не показывает CLAUDE.local.md.
  • Глобальное правило срабатывает в сессии, запущенной в другой папке (например, cd /tmp && claude).
  • Правила для Copilot и Cursor лежат в правильных файлах.
  • В новой сессии агент использует src/log.ts, а не console.log. В docs/notes.md записано, чем агент логировал до и после CLAUDE.md и почему.
  • К итоговому заданию git log --oneline -- CLAUDE.md показывает не меньше 3 коммитов: создание и две правки.
  • В docs/notes.md — две строки из блока «В Copilot и Cursor»: про файл правил и про личное правило в Cursor.
  • В docs/notes.md: какой стек вы выбрали бы для нового сервиса, который в основном будут писать агенты, — популярный или внутренний фреймворк компании, и почему. Опирайтесь на то, что увидели в шагах 1 и 6.
Подсказки
  • Команда /init создаёт черновик CLAUDE.md по коду проекта. Сократите его до главного: агент читает файл в каждой сессии, и лишнее занимает контекст.
  • В новых версиях Claude Code вместо CLAUDE.local.md рекомендуют импорт личного файла из домашней папки (@~/.claude/…). Подойдёт любой вариант: главное, что личные правила не в репозитории.
  • Три уровня: CLAUDE.md — команда и один проект, CLAUDE.local.md — вы и один проект, ~/.claude/CLAUDE.md — вы и все проекты.
  • Cursor и Copilot читают ещё и AGENTS.md. Чтобы не дублировать правила, держите общий текст в AGENTS.md, а в CLAUDE.md подключите его строкой @AGENTS.md.

# CLAUDE.md
## Стек
- TypeScript (strict), Node.js 20+, Express 5, Vitest + supertest, ESLint.
- Хранилище — в памяти (src/storage.ts). Сборки нет, запуск через tsx.

## Команды
- Запуск: npm run dev
- Проверка: npm run check (tsc --noEmit, eslint, vitest). Запускай после каждой правки.

## Конвенции
- Логирование только через getLogger() из src/log.ts, никаких console.log.
- Без any и без non-null assertion (!), типы входных данных описывай явно.
- Тесты — в tests/, файл <модуль>.test.ts, describe по эндпойнту или функции.
- Новый эндпойнт: тип запроса и роут в src/app.ts, логика в src/storage.ts, тест.
- Коммиты: test: / feat: / fix: / chore: и номер тикета, например "test: title validation (T-5)".

## Запреты
- Не меняй файлы, которые не относятся к задаче.
- Не добавляй зависимости без моего согласия.
- Не читай и не выводи .env.
- Не делай git push и merge: это решает человек после ревью.
# CLAUDE.local.md — не коммитится (есть в .gitignore)
- Тесты запускай так: npx vitest run --bail 1
- Перед правкой показывай план из 3–5 пунктов.
# ~/.claude/CLAUDE.md — для всех проектов на этом ноутбуке
- Отвечай кратко, без пересказа того, что ты сделал.
# docs/notes.md, раздел 3.1 (пример)
До CLAUDE.md агент добавил console.log("task done", id): про src/log.ts он не знал,
это «внутренний» код, которого нет в открытых проектах. После правила — getLogger("app").
Вывод: правила в репозитории делают поведение агента одинаковым для всей команды и улучшаются вместе с проектом. Именно это отличает команды с большим приростом продуктивности от команд, где каждый пишет свои промпты. И поэтому для работы с агентами выбирают популярный стек: всё, чего нет в открытом коде, агенту приходится объяснять.
Задание 3.2

Отладка, тесты и декомпозиция

Курсы: AI-Assisted Engineering; Cursor Basics 101 Время: ~60 мин
Что делаем: промпты для тестов, исправления бага и разбиения задачи. Зачем: если дать агенту только код, он напишет тесты, которые подтверждают баг. Если сказать только «почини», исправление будет наугад.

Условие

  1. T-1. Попросите тесты для percent() из src/stats.ts, передав только код. Посмотрите, что проверяют эти тесты. Затем повторите, добавив бизнес-смысл: что функция должна возвращать.
  2. T-2. Исправьте падение GET /tasks/recent промптом из трёх частей: точное сообщение об ошибке, фрагмент кода, ожидаемое поведение.
  3. T-4. Разбейте расплывчатый тикет на подзадачи: каждая независимо полезна, есть иерархия и зависимости.
  4. Галлюцинация. Создайте src/export-draft.ts с кодом ниже — так агент мог ответить на просьбу «сделай экспорт в CSV». Запустите npm run check, проверьте по документации Express, есть ли такая функция, и верните ошибку агенту как обратную связь. Затем удалите файл: T-4 полностью делается в 3.3. 
import { toCsv } from "express";

import type { Task } from "./storage";

export function exportCsv(tasks: Task[]): string {
  return toCsv(tasks, { header: true });
}

Критерии готовности

  • Тесты из второго промпта для T-1 падают на исходном коде и проходят после исправления.
  • Промпт для T-2 из трёх частей записан в docs/notes.md.
  • В docs/notes.md — ошибка tsc из шага 4, ссылка на документацию и ваш промпт с обратной связью.
  • Декомпозиция T-4 записана в docs/T-4.md: подзадачи, иерархия, зависимости.
Подсказки
  • Сначала добейтесь, чтобы тест упал, и только потом исправляйте код. Тест, который не падал ни разу, ничего не доказывает.
  • Подумайте, почему tsc не заметил ошибку в recent(). Посмотрите опцию noUncheckedIndexedAccess в tsconfig.json: это ещё одна детерминированная проверка, которая ловит такие баги до запуска.
  • Сообщение об ошибке и стек возьмите из вывода npm run dev после запроса curl localhost:3000/tasks/recent. В тестах Express стек не печатает, там будет только статус 500.
  • Обратная связь агенту — это факт, а не «попробуй ещё»: точное сообщение компилятора и то, что вы нашли в документации.

Задание 3.3

Spec Kit: от расплывчатого тикета к задачам

Курсы: Spec-Driven Development with GitHub Spec Kit; EngX.AI Bootcamp Время: ~90 мин
Что делаем: реализуем T-4 через полный цикл Spec Kit. Зачем: неточное требование — главная причина того, что агент делает «не то». Спецификация задаёт и цель, и критерии приёмки.

Условие

  1. Установите Spec Kit в проект: uvx --from git+https://github.com/github/spec-kit.git specify init --here --ai claude.
  2. Constitution: правила, которые действуют на каждом шаге — тесты сначала, без новых зависимостей без обоснования, только локальный запуск.
  3. Specify по тикету T-4.
  4. Разберите все метки NEEDS CLARIFICATION: ответьте на вопросы или поправьте спецификацию, затем проверьте её.
  5. Plan → tasks → implement.
Названия команд зависят от версии Spec Kit: /speckit.constitution, /speckit.specify, /speckit.clarify, /speckit.plan, /speckit.tasks, /speckit.implement. В старых версиях — /constitution, /specify, /plan, /tasks.

Критерии готовности

  • В constitution не меньше 3 проверяемых правил.
  • В спецификации перед запуском plan нет меток NEEDS CLARIFICATION.
  • Есть файл задач, и реализация закрывает все критерии приёмки из спецификации.
  • npm run check проходит.
Подсказки
  • Spec Kit — утилита на Python, но проект может быть на любом языке. Для установки нужен uv (brew install uv, pip install uv или по инструкции на сайте uv).
  • Правило в constitution проверяемое, если можно ответить «да» или «нет»: «у каждой экспортируемой функции в src/ есть тест», а не «код должен быть качественным».
  • Метки NEEDS CLARIFICATION — это вопросы к вам. Если пропустить их, решения за вас примет агент.

Задание 3.4

Агентный режим, «сначала тесты» и проверка

Курсы: Structured Vibe Coding; EngX.AI Bootcamp; GitHub Copilot Capabilities Время: ~75 мин
Что делаем: работаем с агентом в цикле «план → тесты → код → проверка». Зачем: вывод агента недетерминирован, поэтому его нужно сочетать с детерминированными проверками. Человек — navigator: задаёт направление, проверяет, останавливает и откатывает агента. Агент — driver: пишет код. Решение «готово к merge» остаётся за человеком.

Условие

  1. Работайте в отдельной ветке, например task-3.4.
  2. T-3 и T-5 по принципу ping-pong: сначала агент пишет тесты на правило (ping) — коммит; затем меняет код, пока тесты не пройдут (pong) — коммит.
  3. Выбор режима. Перед T-6 включите режим плана и задайте вопрос без правок: «где в проекте console.log и как их заменить?» Это аналог Ask: агент читает код, но ничего не меняет.
  4. T-6 в агентном режиме: замена console.log на логгер во всех файлах и правило ESLint no-console, чтобы console.log не вернулся. Агент сам запускает npm run check и исправляет ошибки, пока проверка не пройдёт.
  5. Navigator. Хотя бы раз остановите агента (Esc), когда он уходит не туда, и хотя бы раз откатите его правку (/rewind).
  6. Прочитайте весь diff и найдите хотя бы одно замечание: лишняя правка, пропущенный случай, слабый тест.
  7. Слейте ветку в main сами, после ревью. Агент push и merge не делает: это запрет из CLAUDE.md.

В Copilot и Cursor

Режимы работы.
  • Аналог: в Copilot inline completion — подсказка у курсора; Ask — отвечает и исследует код без изменений; Plan — исследует задачу и составляет план на ревью; Agent — меняет несколько файлов, запускает команды в терминале и повторяет, пока цель не достигнута. В Cursor — Tab, Ask и Agent. В Claude Code режим плана соответствует Ask и Plan, обычный режим — Agent, аналога inline нет. В старых версиях Copilot был ещё режим Edit.
  • С чем путают: Ask и Plan не меняют код и не запускают тесты, поэтому задачу «правка в нескольких файлах и тесты до зелёного» они не решат. Inline completion работает в одной точке файла и ничего не запускает.
  • В журнал: какой режим Copilot подошёл бы к каждому шагу этого задания и почему.

Критерии готовности

  • В истории коммит с тестами идёт раньше коммита с реализацией, и на коммите с тестами они красные.
  • npm run check проходит.
  • git diff --stat показывает изменения только в файлах задачи.
  • Есть хотя бы одно замечание из ревью и его исправление.
  • В docs/notes.md: какие шаги вы делали в режиме плана, а какие в агентном, и какой режим Copilot (inline, Ask, Plan, Agent) подошёл бы к каждому, с одной фразой «почему».
  • В docs/notes.md: когда вы остановили или откатили агента и почему.
  • Merge в main сделан вами после ревью, а не агентом.
Подсказки
  • Режим плана в Claude Code включается сочетанием Shift+Tab: агент показывает план и ничего не меняет, пока вы не согласитесь.
  • Проверить, что тесты были красными: git checkout <коммит с тестами> && npm test, затем git checkout -.
  • Esc останавливает агента и сохраняет историю: можно сразу поправить направление. /rewind (или двойной Esc) возвращает код и диалог к точке до правки.
  • Перед сессией с агентом сделайте коммит: так любую неудачную правку можно откатить и через git.

Задание 3.5

Свои команды, hooks и MCP

Курсы: Claude Code in Action; Cursor Basics 101; GitHub Copilot Capabilities; AI-Native SDLC Время: ~75 мин
Что делаем: превращаем повторяющиеся действия в команды и правила, которые срабатывают автоматически. Зачем: то, что делается чаще двух раз, должно быть командой. То, что нельзя нарушать, должно быть hook, а не просьбой в CLAUDE.md.

Условие

  1. Команда .claude/commands/new-endpoint.md: пошаговый шаблон нового эндпойнта — тип запроса, функция хранилища, роут, тест, npm run check.
  2. Hook PreToolUse: блокирует чтение .env с понятным сообщением.
  3. Hook PostToolUse: после правки .ts-файла запускает eslint для этого файла.
  4. MCP: перенесите 2 тикета из BACKLOG.md в Issues своего репозитория на GitHub, подключите GitHub MCP и реализуйте один тикет, который агент читает через MCP.
  5. Контекст. Попросите тесты для одной функции из src/storage.ts и доведите их до зелёного, даже если понадобится несколько итераций. Затем сделайте /compact и попросите тесты для следующей функции из того же файла. Перед несвязанной задачей сделайте /clear.
  6. Общие настройки команды. Закоммитьте .claude/commands/, .claude/hooks/ и .claude/settings.json. Проверьте, что новый участник получит их при клонировании: git clone . /tmp/team-tasks-check, npm install, запустите там Claude Code.

В Copilot и Cursor

MCP для трекера.
  • Аналог: в Copilot в VS Code сервер описывается в .vscode/mcp.json, в Cursor — в .cursor/mcp.json. Файл можно закоммитить, чтобы сервер был у всей команды; токен в него не кладут.
  • С чем путают: вставлять тикеты в чат вручную — работает, но каждый раз заново и без обновлений. Ссылка на тикет в файле правил — это только текст: открыть её агент не может. Модель побольше не даёт доступа к трекеру.
  • В журнал: почему ссылка на тикет в файле правил не даёт агенту прочитать тикет. 
// .vscode/mcp.json
{
  "servers": {
    "github": { "type": "http", "url": "https://api.githubcopilot.com/mcp/" }
  }
}
Команда для повторяющегося промпта.
  • Аналог: в Cursor — .cursor/commands/*.md, вызывается через /; в Copilot — .github/prompts/*.prompt.md. Формат тот же: Markdown с пошаговой инструкцией, поэтому new-endpoint.md можно перенести почти без правок.
  • С чем путают: личный файл с промптом, который вставляют каждый раз, — он не общий и не версионируется. Просьба «сделай по обычной структуре» заставляет агента угадывать. Документ об архитектуре в каждом запросе занимает контекст, но шагов не задаёт.
  • В журнал: почему команда должна быть пошаговой, а не «сделай как обычно».

Критерии готовности

  • Команда, вызванная дважды для разных эндпойнтов, создаёт одинаковую структуру файлов и тестов.
  • Попытка агента прочитать .env блокируется с сообщением.
  • После правки файла eslint запускается автоматически.
  • PR ссылается на Issue, который агент прочитал через MCP.
  • В docs/notes.md: что агент помнил после /compact и чем это отличалось от /clear.
  • В клоне репозитория команда /new-endpoint доступна и чтение .env блокируется без дополнительной настройки.
  • В docs/notes.md — две строки из блока «В Copilot и Cursor»: про ссылку на тикет и про пошаговую команду.
Подсказки
  • В тексте команды аргументы подставляются через $ARGUMENTS.
  • Hook получает описание вызова инструмента в stdin в виде JSON. Код выхода 2 блокирует вызов, а текст из stderr получает агент.
  • /compact сжимает историю и сохраняет то, что агент узнал. /clear начинает с чистого листа — для новой, несвязанной задачи.
  • Hooks написаны на Node.js (.mjs), поэтому работают одинаково на macOS, Linux и Windows.
  • .claude/settings.json — общие настройки, они в репозитории. .claude/settings.local.json — личные, он в .gitignore.
  • Так работает AI Champion: собирает общие настройки агента в репозитории, чтобы команда работала с ними, а не каждый со своими промптами. Это шаг от L1 к L2.
  • Подключение GitHub MCP требует personal access token.

// .claude/settings.json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Read|Edit|Write|Bash|Grep",
        "hooks": [{ "type": "command", "command": "node .claude/hooks/block-env.mjs" }]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "node .claude/hooks/lint-after-edit.mjs" }]
      }
    ]
  }
}
// .claude/hooks/block-env.mjs
import { readFileSync } from "node:fs";

const input = JSON.parse(readFileSync(0, "utf8")).tool_input ?? {};
const target = ["file_path", "path", "command", "pattern"].map((k) => String(input[k] ?? "")).join(" ");
if (/(^|[\s/'"])\.env(?![\w.])/.test(target)) {
  console.error("Чтение .env запрещено правилами проекта.");
  process.exit(2); // код 2 блокирует вызов инструмента
}
// .claude/hooks/lint-after-edit.mjs
import { spawnSync } from "node:child_process";
import { readFileSync } from "node:fs";

const path = JSON.parse(readFileSync(0, "utf8")).tool_input?.file_path ?? "";
if (path.endsWith(".ts")) {
  const result = spawnSync("npx", ["eslint", path], { encoding: "utf8", shell: process.platform === "win32" });
  if (result.status !== 0) {
    console.error(result.stdout);
    process.exit(2); // агент получит замечания eslint и исправит их
  }
}

Итоговое задание модуля

Фича от тикета до PR

Подтемы: 3.1–3.5 Время: 3–4 часа Результат: PR + заметка о решениях
Сценарий: эпик T-7 «Пользователи забывают про задачи. Нужно напоминать о сроках». Требований почти нет — их нужно выяснить и записать.

Путь

Правила проекта → constitution и спецификация → разбор вопросов → план и задачи → реализация «сначала тесты» → своя команда /self-review → npm run check → PR с описанием.

Команду для ревью назовите не /review: в Claude Code уже есть встроенная команда с таким именем.

Критерии приёмки

Подтема Курс Критерий
3.1 Правила Claude Code in Action Агент соблюдает CLAUDE.md без напоминаний; личные правила не в репозитории; CLAUDE.md менялся по ходу модуля (не меньше 3 коммитов).
3.2 Тесты AI-Assisted Engineering Тесты проверяют бизнес-правила из спецификации, а не текущее поведение кода.
3.3 Спецификация Spec Kit; EngX.AI Есть constitution и спецификация без NEEDS CLARIFICATION; каждый критерий приёмки закрыт тестом.
3.4 Проверка Structured Vibe Coding; EngX.AI Коммит с тестами раньше реализации; npm run check проходит; изменения только в нужных файлах.
3.5 Автоматизация Claude Code in Action В работе использованы своя команда /self-review и hooks.
PR EngX.AI В описании: что сделано, как проверено, что осталось. Merge делаете вы после /self-review и чтения diff, а не агент.
Метрики AI-Native SDLC Цифры в заметке взяты из git log и /cost, а не оценены «на глаз»; названа базовая линия для сравнения.
Практика команды AI-Native SDLC Настройки агента в репозитории работают после клонирования; в заметке — уровень L0–L3 вашей команды и следующий шаг.

Заметка о решениях (до страницы)

  • Какие вопросы по требованиям возникли и как они решены.
  • Где агент помог, где пришлось вмешиваться и почему.
  • Метрики из системных данных: число коммитов, время от первого коммита ветки до PR, сколько раз тесты сначала были красными, стоимость сессий (/cost). Оценки вида «сэкономил 3 часа» не считаются.
  • С чем сравнивать: какую базовую линию «до AI» вы взяли бы в своей команде (например, cycle time и число возвратов из ревью по Jira за квартал до внедрения) и почему метрики одной ветки одного человека сами по себе ничего не доказывают. Не годятся опрос «сколько часов сэкономили» и число строк, написанных AI.
  • На каком уровне L0–L3 ваша текущая команда и что из настроек модуля вы бы перенесли в её репозиторий. 
git log main..HEAD --reverse --format='%h %ci %s'   # коммиты ветки и их время
git log main..HEAD --oneline | wc -l                 # число коммитов

Как проверить себя

Подтема Как проверить
3.1 Правила git log --oneline -- CLAUDE.md — не меньше 3 коммитов; git ls-files CLAUDE.local.md ничего не выводит; в diff ветки нет нарушений правил из CLAUDE.md.
3.2 Тесты Временно нарушьте одно бизнес-правило в коде (например, срок напоминания) и запустите npm test: хотя бы один тест должен упасть. Затем git restore ..
3.3 Спецификация grep -rn "NEEDS CLARIFICATION" specs/ ничего не выводит; для каждого критерия приёмки из spec.md найдите тест, который его проверяет.
3.4 Проверка git log --oneline main..HEAD: коммит test: раньше feat:; git checkout <коммит с тестами> && npm test — красный; npm run check — зелёный; git diff --stat main...HEAD — только файлы задачи.
3.5 Автоматизация Команда /self-review лежит в .claude/commands/; в docs/notes.md записано, где сработал hook и что сказал /self-review.
PR В описании три раздела: что сделано, как проверено, что осталось.
Метрики У каждой цифры в заметке указана команда, из которой она взята; есть базовая линия и источник данных для неё.
Практика команды git clone . /tmp/team-tasks-check, npm install, Claude Code: команда /new-endpoint есть, чтение .env блокируется.

Вопросы по T-7 и решения (фрагмент spec.md):
- Где хранится срок? Новое необязательное поле dueDate (ISO-дата) у задачи.
- Что такое «напоминать»? GET /reminders: невыполненные задачи со сроком
  в ближайшие 24 часа и просроченные. Почта и push — вне объёма.
- Срок в прошлом при создании? 422 с { detail }.
- Выполненные задачи? В напоминания не попадают.
Описание PR (пример):
## Что сделано
T-7: поле dueDate, валидация срока, GET /reminders (просроченные и ближайшие 24 ч).
## Как проверено
npm run check зелёный; 9 тестов по критериям приёмки AC-1…AC-5 из spec.md;
тесты закоммичены до реализации (a1b2c3d → d4e5f6a).
## Что осталось
Уведомления по почте — отдельный тикет; часовой пояс пользователя не учитывается.
Заметка (фрагмент про метрики):
- 7 коммитов в ветке (git log main..HEAD --oneline | wc -l).
- 2 ч 40 мин от первого коммита до PR (git log main..HEAD --reverse --format='%ci').
- Тесты были красными до реализации в 2 из 2 пар test/feat.
- $1.85 за сессии (/cost).
- Базовая линия: медианный cycle time похожих тикетов в Jira за квартал до AI — 3 дня.
  Одна ветка — это точка, а не тренд: сравнивать нужно медианы команды за период.
Если какой-то критерий не выполнен: вернитесь к заданию и курсу из колонок «Подтема» и «Курс».
